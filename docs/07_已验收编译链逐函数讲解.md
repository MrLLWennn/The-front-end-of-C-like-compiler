# 已验收编译链逐函数讲解

本轮不是继续加代码，而是将已经跑通的受限链路对应到函数、数据和验证证据。所有构建、链接和执行均由用户完成；助手只读取这些产物并维护文件。

## 前后职责变化

原链路重点是源文件到 Token、语法推导、DOT 树和符号表；这些是观察前端过程的结果，机器不能直接执行 DOT 图。现在新增同一份 Token 到语义 AST 的桥接，再转换为 LLVM IR，运行标准优化管线并生成原生目标文件，由 clang 驱动完成链接。

main 仍负责选项、路径检查、配置和统一错误边界。legacy 走原来的 compiling；ast/llvm 走 build_typed_program。FrontEnd 先执行原 Lexer 和表驱动 Parser，再由 ast::build 对同一份 Token 做结构遍历。没有解析 DOT，也没有绕过原 Parser。代价是两次结构识别，后续才把 AST 构造融入原语法匹配，不把这一过渡实现称为前端加速。

## AST 表达含义与所有权

`int calc(int x, int y) { return x + y * 2; }` 的 AST 是一个返回节点，下面的加法左边为 x，右边为乘法 y*2。中间文法节点 expression/term/factor 不必都保留给后端。

Builder::function 读取函数名和参数，要求 int 参数与返回值，函数体目前只有一条 return。Builder::primary 读取整数、名字和括号；from_chars 检查整个词素是否都是合法十进制整数且没有越界。Builder::expression 使用优先级爬升：+/-为10，*为20；右侧递归门槛设为 priority+1，允许更高优先级进入右子树，同优先级留给外层按左结合处理。由此 x+y*2 是 x+(y*2)，x-y-z 是 (x-y)-z。

AST 的子节点用 unique_ptr 独占，std::move 把孩子的所有权交给父节点，不复制整棵子树。源 Token 在 Builder 内借用，Program 返回后独立拥有其 AST。check_names 检查重复函数、重复参数，以及表达式的名字是否能在参数集合中找到；当前不是完整 C 作用域或通用类型推导。

## AST 到 LLVM IR

llvm_backend::emit 创建 TargetMachine、LLVMContext、Module、IRBuilder。Context 管理类型和常量等基础数据，Module 组织函数，Function 容纳基本块，IRBuilder 在当前插入点创建指令。声明顺序使 Module 和 Builder 在 Context 之前析构。

FunctionType::get 描述返回/参数 i32；Function::Create 建立函数，BasicBlock::Create 建立 entry，SetInsertPoint 指定指令落点。names 把参数名映射到 LLVM Argument 的 Value*；这些指针是非拥有引用，不由本项目手动delete。我们自己的 AST 与 LLVM IR 分开管理生命周期。

后端 expression 递归处理节点：整数转 ConstantInt；名字查 names；加减乘先生成两侧操作数，再调用 CreateAdd/CreateSub/CreateMul，最后 CreateRet 返回结果。这些函数创建 IR，不直接执行运算。

真实生成的 calc 原始 IR：

```llvm
define i32 @calc(i32 %x, i32 %y) {
entry:
  %mul = mul i32 %y, 2
  %add = add i32 %x, %mul
  ret i32 %add
}
```

i32 表示32位整数，@calc 是全局函数名，%x/%y是参数，%mul/%add是SSA值的名字；不是源码中的可变内存单元。当前子集把加减乘定义为32位回绕，因此没有随意添加 nsw/nuw。它与完整C的有符号溢出规则不能混称。

## 优化与证据

IRBuilder 使用 NoFolder，让常量折叠不会在构建时提前混入观察结果；保存16-before.ll后，再由 optimize 选择O0不运行管线或O2运行标准模块管线。优化前后都调用 verifyModule，检查 IR 结构与类型一致性；verifier 不证明源语言翻译或运行结果正确，所以仍要链接执行验证。

当前真实 simplify 产物：优化前 `%add = add i32 %x, 0; ret i32 %add`，O2之后直接 `ret i32 %x`。calc的O2实际产物还把 `%mul = mul i32 %y, 2` 改为 `%mul = shl i32 %y, 1`。这些变换来自LLVM标准管线；本项目完成的是AST桥接、IR构造、管线配置和验证，不称自研这些Pass。IR指令变少也不能直接当成实测速度提升。

## 目标文件与链接

TargetMachine 决定目标平台、数据布局和原生目标代码生成。18-program.o 含目标代码，但本项目仍由 clang 驱动链接启动文件、运行库等，得到可执行程序。测试中的C harness由clang编译后调用我们生成的函数，用于验证调用与结果；没有把输入源码交给clang重新生成该函数的目标文件。

语法/名字/IR校验失败时不发布新的LLVM产物；多文件写出不是原子事务，I/O中途失败仍可能残留部分文件，使用新的输出目录。SourceManager原始位置映射、局部变量/作用域、if/while、函数调用和运行库仍是后续包，当前只验收明确子集。

## 面试预测与参考答案

**为何还需要AST？** 原推导树保留文法过程，后端需要运算、名字、常量和类型。增加独立AST表示，避免LLVM代码依赖每条文法改写细节。

**参考LLVM的哪部分，自己项目的工作在哪里？** 参考官方前端教程的AST到IR分层与New Pass Manager使用方式，结合原表驱动前端增加AST桥接、名字检查、可选后端模块、CLI选择、产物保护和源到运行回归；复用LLVM标准优化与目标后端。

**如何证明优化正确？** 保存前后IR观察变换，O0/O2生成的目标分别链接同一测试程序，以多组输入检查输出；错误路径核对退出码、诊断与无成功产物。verifier与运行测试相互补充，选定测试不是数学等价证明。

**CMake如何组织？** compiler_core包含前端和AST；compiler_llvm仅在选项开启时构建，隐藏LLVM头文件依赖；my_compiler保留入口。target_link_libraries表达依赖，不把LLVM类型直接泄露到前端公共接口。当前已验证开启LLVM配置，关闭配置的当前源码完整回归未另跑，不扩称所有配置均过。

**现在最明显的结构代价是什么？** 保留原Parser后又遍历Token构建AST，存在重复结构识别；旧文法还保留特殊选式与可空回退，不宣称已成为任意文法通用LL(1)生成器。
