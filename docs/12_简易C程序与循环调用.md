## 为什么增加这几项

此前已经能为带局部变量和if/else的int函数生成目标文件，但演示主要依靠外部调用程序。希望由自己的源码提供main，并在一个程序里调用辅助函数、重复计算、检查结果，需要补上函数调用、整数比较和while循环。

本轮不追求完整C语言。验收样例是examples/mini_c.c：square计算平方，sum_squares循环累加，main检查5、0、10的平方和是否分别为55、0、385。任一检查失败返回1/2/3，全部正确返回0。它没有标准输出；演示脚本负责解释结果，不能把脚本的中文提示说成编译器已经支持printf。

## 一条完整链路的职责

源码 → 既有预处理/Lexer/表驱动Parser → AST Builder → 语义检查 → LLVM IR → 标准O0或O2路径 → 原生目标文件 → Clang链接 → 执行main。

两个解析层的区别保持不变：表驱动Parser先检查旧文法；AST Builder再提取本项目有后端支持的结构。新测试要求原Parser留下“预测分析结束”记录，防止为演示绕开原来的前端。因此旧文法的声明顺序及部分表达式限制仍存在；本轮没有把整个前端重写成Clang。

## AST Builder如何补齐结构

原Expression只保存整数、名字、一元和二元表达式；二元运算符是char。现在增加Call，函数名放在name，arguments独占实参表达式；operation改为string，从而完整保存<=、==等双字符运算符。父节点仍用unique_ptr拥有子节点，std::move只转交所有权，不复制整棵树。

primary读到标识符后查看下一个Token：如果是左括号，就解析逗号分隔的实参列表，构成Call；否则仍是普通变量。这样inc(inc(n))会形成两层调用节点。函数调用作为表达式参与计算，不新增独立的“忽略返回值调用”语句。

precedence加入比较：乘20，加减10，关系比较7，相等比较5。优先级爬升仍通过右侧门槛priority+1保持左结合。不过旧文法只允许一层未加括号的比较，因此不宣称支持任意连续比较；需要组合时明确加括号。

statement增加While，独占condition和body，循环体要求花括号。原Conditional及其then/else字段保持原职责，不把循环体硬塞进then_branch。函数仍要求顶层最后一条return，不支持循环内return、break或continue。

## 语义检查为何不能省

### 先确认调用合法，再生成call

原check_names只用集合发现重复函数名。现在Functions记录“函数名→参数个数”；按源码顺序，在检查当前函数体前登记当前函数。因此允许调用此前定义的函数和自递归，不允许无原型的前向调用。后端预建所有LLVM函数签名只是生成策略，不能倒过来放宽前端的可见性规则。

check_expression遇到Call依次检查：局部/参数是否遮蔽函数名；函数是否可见；实参数量是否相同；每个实参是否可以合法求值。缺少函数和把局部变量当函数调用报E_SEMA_CALL；参数个数错误报E_SEMA_ARGUMENTS；实参读未初始化变量沿用E_SEMA_UNINITIALIZED。

没有建立完整类型系统。因为所有值和参数都是int，本轮只检查数量，不宣称做了重载解析、隐式转换或完整C类型兼容检查。

### 循环可能执行零次

例如：`int value; while(n) { value = 1; n = 0; } return value;`。n一开始为0时，value没有值。因此循环体在入口Scopes的副本上检查，循环结束保留原入口状态。循环内先给value赋值再读取可以通过，但仅在循环内赋值不能让循环后的读取自动通过。

这是保守的确定初始化检查，不是循环终止证明或完整数据流不动点求解。即使人工能推断某个条件必真，本实现也可能拒绝依赖“至少执行一次”才安全的程序。

## LLVM部分具体改了什么

### 比较结果：i1转为i32

原expression只生成add/sub/mul；现在六种比较分别生成有符号icmp slt/sle/sgt/sge或eq/ne。icmp返回i1，但源语言比较的值要作为int的0/1继续参与表达式，因此CreateZExt将i1转为i32。不能符号扩展，因为i1的1若符号扩展会变为-1。if/while需要跳转时，再比较该i32是否非0。

### 函数调用：签名先就位，函数体随后生成

emit先为每个函数建立LLVM FunctionType和Function，再逐个创建入口块和函数体。Call生成时到Module查找目标，递归生成实参Value，再CreateCall。参数通过已有入口alloca/store路径成为可赋值的局部名字。源码可见性与参数个数已经由前端检查，后端仍保留内部一致性检查。

### while：条件块、循环体块、出口块

生成结构为：当前块→while.condition；条件非0→while.body，否则→while.end；循环体结束→while.condition。条件中的load和函数调用放在条件块里，所以每轮重新读取变量。若只在循环外算一次条件，就可能让该退出的循环永远无法退出。

循环体递归生成嵌套if/while后，IRBuilder的当前位置可能已经不是最初的while.body。回边从当前实际末块发出，避免在已经有跳转指令的块后继续追加。循环之后的语句从while.end继续生成。

局部alloca仍统一放在函数入口，声明的初始化store在实际执行位置。循环中的声明不会每轮重新扩展一段栈空间；其名字绑定仍随词法块进入和退出。O2可能提升或消除这些槽位，但本轮不固定要求优化后的IR保留某种循环形状。

此设计参考[LLVM官方控制流教程](https://llvm.org/docs/tutorial/MyFirstLanguageFrontend/LangImpl05.html)的基本块、条件跳转及嵌套生成后更新当前块的做法，以及[LLVM IRBuilder接口](https://llvm.org/doxygen/classllvm_1_1IRBuilderBase.html)的调用和比较接口。本项目实现的是int子集的while与语义检查，教程中的Kaleidoscope浮点语言和for表达式不能直接照搬。

## 如何验收

在仓库根目录运行：

```bash
cmake --workflow --preset frontend-check
cmake --workflow --preset llvm-check
python3 examples/run_mini_c.py build-presets/llvm-debug/my_compiler --opt-level 0
python3 examples/run_mini_c.py build-presets/llvm-debug/my_compiler --opt-level 2
```

当前预期注册9项前端CTest、13项LLVM配置CTest。两套有重叠，不相加成22种独立测试。

新增程序语义测试：21个函数正例、1个完整程序、17个拒绝用例，共39例。新增程序原生测试：21个函数正例分别O0/O2×9组输入，共378次calc调用；完整main程序分别O0/O2运行；17个拒绝用例，共61项用例。

运行对照使用独立Clang编译同一份合法C源码及同一个调用程序，比较输出；求和案例额外核对数学公式。固定输入覆盖负数、0、1及多次迭代，递归只用有限安全输入；不会生成有除零、溢出或无限循环的性能样本。subprocess有超时，错误回边不会无限卡住测试。

每次新建目录，检查源码与文法字节未改变；拒绝用例不能留下15/16/17/18最终产物。用例覆盖函数名遮蔽、错参数、未初始化、循环作用域，以及本轮明确不支持的功能。通过这些测试只证明覆盖范围内行为，不能据此声称完整C兼容、循环一定终止或性能提高。

失败时优先给出第一项失败的完整诊断及日志目录，不需要反复贴所有构建输出。可单独运行：

```bash
ctest --test-dir build-presets/llvm-debug -R '^compiler_program_' -V
```
