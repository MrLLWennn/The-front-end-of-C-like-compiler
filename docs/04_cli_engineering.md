## 为什么做

旧main只构造编译器；所有阶段使用header_files.h中各翻译单元自己的static const字符串，写死../files。调用方必须创建特定files/work布局，难以被脚本或容器调用。input_file用fstream默认in|out打开输入，纯读取也要求写权限；失败返回值常被忽略。

新版main负责参数→校验→绑定路径→调用核心→捕获异常/退出。app/driver_options负责CLI与文件边界，CompilationPaths保存一次运行的输入和输出；原核心和预测算法保留。

## 修改前后

| 位置 | 原来 | 修改后及理由 |
|---|---|---|
| main.cpp | 无参数，固定返回0 | 支持--input/--grammar/--output-dir/--help；使用错误2、文件或运行异常1 |
| include/my_compiler/compilation_paths.hpp | 无运行配置对象 | 值对象集中描述路径；默认值保留探针兼容；旧模块暂经共享适配器读取 |
| header_files.h | 每个翻译单元静态常量副本 | 只读引用绑定同一适配器中的字段，显式调用更新字段后旧模块看到一致路径 |
| header_files.cpp | 输入默认in|out，失败返回值容易被忽略 | 输入显式ios::in；打开失败抛异常到driver，避免继续读写无效流 |
| app/driver_options.* | 无 | 检查参数、输入可读和输出不覆盖输入；先全部检查，再创建输出目录 |
| CMakeLists.txt | core＋CLI＋两组回归 | 保留原目标，添加include路径、driver源文件与CLI集成测试 |

这是渐进式架构改进。共享适配器还不支持同进程并发，今后可把配置直接注入Lexer/Parser来移除隐式状态；本轮不伪装为已彻底解耦。若新需求要求服务内并发编译，应先消除共享状态；当前只支持分进程隔离。未添加LLVM依赖，参考的是其命令行工具把配置/输入/错误暴露给调用方的设计。[LLVM CommandLine](https://llvm.org/docs/CommandLine.html)。

## 验证与失败语义

用户执行README中的同目录configure/build/ctest命令。新增回归分别断言状态和具体错误原因：未知/重复/缺参；缺源文件/文法；输出路径是普通文件；输入与输出同路径或硬链接；合法只读输入和带空格路径；任意工作目录；两个独立进程输出隔离。检查源文件与文法不变，不能以任意非零退出代替测中目标失败。

旧最小端到端检查继续核对Token、无解析错误日志、DOT/SVG；FOLLOW五类模块检查继续保留。CLI的正常退出仍不代表任意源码语法正确：结构化词法/语法诊断和统一失败状态留在UR02。没有加入性能提升主张。

## 预计面试追问与参考答案

**导师：为什么先改路径而不是多支持一种语法？** 旧工作目录约束直接影响可重复调用、测试隔离与容器只读输入。先明确输入输出和失败条件，之后加功能能复用稳定入口。

**导师：配置对象是不是完全消除了全局状态？** 没有。配置已值化，但旧阶段暂经共享适配器取值；文档明确一进程一次运行。完整依赖注入是下一阶段，不把当前状态说成线程安全。

**导师：为什么不直接引入LLVM？** 本轮借鉴其工具边界而保留本人前端，避免在一周内引入大依赖和迁移解析架构。LLVM本身的IR/JIT和后端不是本轮完成范围。

**HR：哪些是本人贡献？** 旧前端本人编写；本轮代码与测试脚手架由助手实现和解释，本人完成后续构建、故障核对与选择判断。本轮已由本人执行3项回归并通过；独立设计和独立排错能力仍需另外核验。

**导师：如何在Docker里使用？** 源码/文法可只读挂入，输出挂到独立可写目录；明确传入容器内路径。镜像兼容性、构建环境、应用退出和产物都要验证，不能只看容器Up。Docker演示是后续用户实践，尚未完成。
